# Mail Agent AI Code Conduct

## 1. 목적

이 문서는 Mail Agent 프로젝트에서 AI가 코드를 읽고, 수정하고, 추가할 때 따라야 할 기본 행동 규범을 정의한다.

목표는 다음과 같다.

- 제품 방향과 일치하는 코드를 작성한다.
- 불필요한 변경을 줄인다.
- 안전하고 복구 가능한 방식으로 수정한다.
- 일관된 구조와 품질을 유지한다.

## 2. 최우선 원칙

AI는 항상 다음 우선순위를 따른다.

1. 데이터 신뢰성
2. 보안과 권한 최소화
3. 동기화 정확성
4. 유지보수성
5. 사용자 경험
6. 개발 속도

빠르게 만드는 것보다, 나중에 깨지지 않는 구조를 우선한다.

## 3. 제품 이해 원칙

AI는 이 프로젝트를 다음과 같이 이해하고 작업한다.

- Mail Agent는 단순 메일 클라이언트가 아니다.
- 여러 메일 계정을 통합하는 작업 공간이다.
- Notion은 메일 원본 저장소가 아니라 작업/기록 연계 대상이다.
- AI는 초기에는 자동 실행 주체가 아니라 분석과 추천 보조자다.
- Provider 차이는 내부 정규화 모델 뒤로 숨겨야 한다.

이 원칙과 충돌하는 구현은 피한다.

## 4. 작업 전 행동 규칙

- 먼저 기존 코드와 문서를 읽고 현재 구조를 이해한다.
- 추측보다 현재 구현과 문서에 맞춘다.
- 한 번에 큰 구조 변경보다 작은 단위로 나눈다.
- 수정 범위를 최소화한다.
- 관련 없는 코드 스타일 변경은 하지 않는다.
- 사용자가 요청하지 않은 리팩터링은 함부로 확장하지 않는다.

## 5. 설계 원칙

### 5.1 정규화 우선

- Gmail, IMAP, Outlook 차이를 그대로 상위 계층에 노출하지 않는다.
- Provider 전용 로직은 Connector 계층에 가둔다.
- 상위 계층은 `Account`, `Message`, `Thread`, `Attachment`, `Label` 같은 내부 모델 기준으로 동작해야 한다.

### 5.2 비동기 작업 분리

- 오래 걸리는 작업은 요청-응답 흐름에 직접 묶지 않는다.
- 동기화, AI 분석, Notion 반영, 재시도 작업은 Queue/Worker로 분리한다.
- 실패 가능성이 높은 외부 연동은 재시도 가능하게 설계한다.

### 5.3 사용자 확인 우선

- 삭제, 발송, 보관, Notion 생성, 자동 처리 같은 액션은 사용자 의도 확인을 우선한다.
- AI가 제안할 수는 있지만, 초기 단계에서는 직접 확정하지 않는다.

### 5.4 복구 가능성 확보

- 상태 변경 전후를 추적 가능해야 한다.
- 자동화 액션에는 로그가 남아야 한다.
- 실패했을 때 재시도 또는 수동 복구 경로가 있어야 한다.

## 6. 코딩 원칙

### 6.1 단순성

- 가장 단순하게 읽히는 구현을 우선한다.
- 과도한 추상화는 피한다.
- 동일 패턴이 반복될 때만 공통화한다.

### 6.2 명확한 이름

- 변수, 함수, 클래스 이름은 역할이 드러나야 한다.
- 축약어는 정말 널리 쓰이는 경우만 사용한다.
- `data`, `temp`, `result` 같은 모호한 이름을 남발하지 않는다.

### 6.3 함수와 모듈의 책임

- 함수는 한 가지 책임에 집중한다.
- 하나의 모듈에 Provider 처리, DB 저장, UI 포맷팅을 섞지 않는다.
- 계층 간 역할을 흐리지 않는다.

### 6.4 타입 안정성

- TypeScript 타입을 적극적으로 사용한다.
- `any` 사용은 예외적으로만 허용한다.
- 외부 API 응답은 검증 또는 정제 후 내부 모델로 변환한다.

### 6.5 주석 원칙

- 코드만으로 의도가 분명하면 주석을 추가하지 않는다.
- 왜 이렇게 구현했는지 설명이 필요한 곳에만 짧게 작성한다.
- 코드와 어긋날 가능성이 큰 장문 주석은 피한다.

## 7. 데이터 및 동기화 규칙

- Provider의 원본 ID와 내부 ID를 분리한다.
- 동기화 코드는 중복 저장 방지를 기본 가정으로 작성한다.
- 증분 동기화가 가능하면 전체 재수집보다 우선한다.
- 읽음/보관/삭제 상태는 Provider와 내부 저장소 간 불일치를 줄이도록 설계한다.
- 첨부파일은 초기에는 메타데이터와 provider reference 중심으로 다룬다.

## 8. 보안 규칙

- access token, refresh token, 비밀번호, secret은 평문 저장하지 않는다.
- 로그에 민감 정보가 노출되지 않게 한다.
- OAuth scope는 최소 권한 원칙을 따른다.
- 사용자 메일 본문과 첨부파일은 필요한 범위에서만 다룬다.
- 외부 API 호출 전후에 민감 정보 마스킹 여부를 확인한다.

## 9. Notion 연동 규칙

- 모든 메일을 Notion으로 보내지 않는다.
- 사용자가 명시적으로 요청한 메일만 우선 연동한다.
- DB 스키마 차이를 고려해 mapping 기반으로 구현한다.
- Notion 생성 실패가 메일 원본 상태를 깨지 않도록 분리한다.
- Mail Agent와 Notion의 연결 정보는 추적 가능해야 한다.

## 10. AI 기능 구현 규칙

- AI 결과는 사실이 아니라 추론 결과일 수 있음을 전제로 다룬다.
- 요약, 중요도, 마감일, 답장 필요 여부는 확정값이 아니라 분석 결과로 저장한다.
- AI 결과에는 가능하면 `confidence` 또는 검토 가능성을 남긴다.
- AI는 초기 단계에서 `추천`, `초안`, `후보값` 중심으로 사용한다.
- 자동 실행은 명시적 opt-in과 로그 체계가 갖춰진 뒤에만 허용한다.

## 11. API 작성 규칙

- 입력과 출력 스키마를 명확히 한다.
- 실패 응답은 일관된 형식을 유지한다.
- 외부 API 실패를 내부 예외와 분리해서 다룬다.
- 재시도 가능한 오류와 즉시 사용자 수정이 필요한 오류를 구분한다.
- 사이드이펙트가 큰 API는 idempotency를 고려한다.

## 12. UI 작성 규칙

- 메일 상태는 사용자가 이해할 수 있게 명확히 보여준다.
- Provider 처리 중인 상태, 실패 상태, 재시도 상태를 숨기지 않는다.
- AI 추천은 확정값처럼 보이지 않게 표시한다.
- 사용자의 실제 작업 흐름인 `읽기 -> 판단 -> 처리 -> 기록 연결`을 우선한다.
- 시각적 화려함보다 정보 밀도와 처리 속도를 우선한다.

## 13. 테스트 규칙

- 핵심 도메인 로직은 가능하면 테스트한다.
- 특히 다음 영역은 우선 테스트한다.
  - Message normalization
  - Thread mapping
  - 중복 방지 로직
  - 동기화 증분 처리
  - Notion mapping
  - AI 분석 결과 저장 처리
- 버그를 수정할 때는 가능하면 재현 테스트를 함께 추가한다.

## 14. 로깅 규칙

- 자동 액션은 항상 로그를 남긴다.
- 외부 연동 실패에는 원인 추적 가능한 정보가 있어야 한다.
- 하지만 로그에 본문 전체나 민감 토큰을 남기지 않는다.
- 사용자 액션과 AI 추천 액션은 구분해서 기록한다.

## 15. 문서화 규칙

- 새로운 구조나 규칙을 만들면 최소한의 문서를 함께 갱신한다.
- 구현이 개발 계획과 달라지면 관련 문서를 업데이트한다.
- 임시 결정이 장기 결정처럼 굳어지지 않도록 TODO 또는 제한사항을 남긴다.

## 16. 금지 사항

- 요청받지 않은 대규모 구조 변경
- 민감 정보 평문 저장
- Provider 전용 로직을 상위 계층에 누수시키는 구현
- 실패 복구 경로 없는 자동화
- 로그 없는 자동 액션
- 테스트 없이 핵심 동기화 로직을 크게 변경하는 작업
- 사용자 확인 없이 메일 발송/삭제/대량 보관 처리

## 17. 변경 단위 규칙

- 한 번의 작업은 가능한 한 하나의 목적에 집중한다.
- 기능 추가와 리팩터링과 스타일 변경을 한 커밋 성격으로 섞지 않는다.
- PR 또는 변경 설명은 다음을 포함하도록 한다.
  - 무엇이 바뀌었는가
  - 왜 바꿨는가
  - 어떤 리스크가 있는가
  - 무엇을 검증했는가

## 18. 이상적인 작업 흐름

AI는 가능한 한 다음 순서로 작업한다.

1. 관련 문서와 기존 코드 읽기
2. 영향 범위 파악
3. 최소 변경 설계
4. 구현
5. 테스트 또는 검증
6. 문서 반영
7. 변경 요약

## 19. 이 프로젝트에서 특히 조심할 것

- Gmail과 IMAP을 같은 방식으로 취급하려고 무리하게 단순화하지 않는다.
- Thread, Label, Folder 의미 차이를 무시하지 않는다.
- Notion DB 구조가 사용자마다 다름을 항상 가정한다.
- AI 출력은 언제든 틀릴 수 있다고 가정한다.
- "작동하는 것처럼 보이는 코드"보다 "운영 중에도 버틸 코드"를 우선한다.

## 20. 최종 원칙

이 프로젝트에서 AI의 역할은 빠르게 아무 코드나 추가하는 것이 아니다.

AI의 역할은 다음과 같다.

- 제품 방향을 해치지 않는 코드 작성
- 사람이 나중에 읽고 고치기 쉬운 구조 유지
- 외부 연동과 자동화의 위험을 낮추는 보수적 구현
- 기능보다 신뢰를 먼저 쌓는 개발 보조
